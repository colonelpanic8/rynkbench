# 0019. Operations: named changes from one image to another

**Status:** Accepted. Step 4 of the architecture plan (`docs/architecture-review.md`, "The plan, validated"); the foundation for Flows and WebMCP, which are not built here; imports completed by 0023 as a direct commit, not an operation. Builds on ADR 0018 (the draft is a wanted image) and refines ADR 0016 for the lighting controls.

## Context

Every edit is a commit to what you want (ADR 0018), but the bulk changes do not commit: a transform writes key after key and slot after slot through `io` with the history suspended and cleared; the status setups, lighting key presets, the stock Magic layer and the condition rules panel write their keys at once and the whole rule table beside the draft (todo 10 and 11); an import writes part after part from `config/transfer.ts` and clears the history; a layer move in Live has its own read, plan, rollback and read-back. None of them is one Undo step, and none can be called by code without a screen. A Flow or an assistant needs one thing to call: a named change it can list, preview and apply.

## Decision

**An operation is a named, pure function from one `KeyboardImage` to another** (`sync/image.ts`), in `src/operations/`: `run(image, input, facts) → { ok, image } | { ok: false, message }`. `input` is typed, and described by its fields (name, kind, a short description, a range or the allowed values); `facts` is what the keyboard is but does not store (columns, capacities, the compiled scenes and rules, the active layers). An operation reads nothing, writes nothing and asks nothing. The first ones: `set_keys`, `swap_keys`, `move_layer`, `delete_layer`, `duplicate_layer`, `set_key_light`, `apply_transform`; then the presets, the rule table and imports. `operations/` is a layer between `sync/` and `workbench/`: it imports only `model/`, `domain/`, `layers/`, `sync/`'s pure parts and itself; nothing below the workbench imports it (`boundaries.ts`).

**How one is applied** (`workbench/apply.ts`, `io.apply(name, input)`): run it on what you want; if nothing changes, nothing happens; Guard judges the result against what you want now, through an adapter from `KeyboardImage` to the layout `judgeChange` takes (`operations/guard-input.ts`), and asks or stops as for any key; it becomes one commit (one action, `commit`), so it is one Undo step whatever its size. The mode decides when it is written, as for any edit: in Draft it waits for Send; in Live it is sent at once through the one write path (Send's: fresh read, the difference, read back). In Live it is all or nothing: if the send stops part-way, what you wanted goes back to what it was (joined to the same step, so it leaves no history) and is sent again, so the keyboard is as before; the answer says so, or that putting it back failed too. Guard's questions stay in `ui/guard/` (they need the message store): the screen gives the io a `judge(before, after)`; the io's default lets everything through, for code without a person to ask. Imports and transforms are operations, so they stop suspending and clearing the history. `io.writeKeys` and the layer structure use operations; their callers do not change. A layer operation still reads the keyboard first (every encoder and the layer state, which the draft may lack) and runs on that read with the draft on top.

**The catalog** (`operations/catalog.ts`) lists each operation's name, description and input fields as plain data, and `runOperation(name, image, input, facts)` checks the input against its fields before it runs. WebMCP and Flows will list and call operations through it and `io.apply` without changes to the core. It is data, not tools: nothing is registered, and nothing outside the app can reach it.

**The lighting exception.** RGB Lighting and RGB Effects (on or off, brightness, background, effect, palette, speed, the effect's parameters) get a "Realtime" switch in their own menus: on, a change to them goes to the keyboard at once even in Draft, so you see it on the board as you drag. It is a browser preference (`ui/preferences.ts`, off by default), not a setting of the layout. Keys, layers, scenes, rules and every other setting stay in the draft.
- *Base:* a realtime write is a Live write for those items: when the keyboard answers, `base` holds them, so they are not in the draft, Send does not write them again, and the kept draft does not hold them. The change is still one commit and one Undo step (a slider's drag is one commit); Undo and Redo in Draft write the realtime items they change at once too, so the board and the draft never disagree.
- *Flash:* the controls are stored in flash, so a drag must not write on every move. Realtime writes are throttled: one in flight at a time, at most one every 250 ms, and always the latest value; the value where the drag ends is always written. A drag of a few seconds is a handful of writes, not hundreds.
- *Errors:* a realtime write that fails leaves the items in the draft, where Send writes them; the error shows as a lighting error.

## Consequences

- A new bulk change is one operation and its test; staging, Guard, Send, Undo and Live atomicity come with `io.apply`.
- Transforms, imports and presets are one Undo step, in Draft can be reviewed before they are sent, and in Live leave the keyboard as it was when they fail. Progress counts per write go: a bulk change in Live is one send.
- `layerOperationApplied`, `layerRewriteDrafted` and the history's suspend go; the Live layer path's own read-back and rollback are replaced by the general ones.
- The way there is three parts, each green before the next: the layer, catalog, apply path and first operations; the bulk writers; the realtime lighting switch.
